# Security trade-offs

The risks this project accepts, each with why it's a risk and the fix for production. Numbered so reviews can cite them (trade-offs 1). An accepted risk is a decision: change it here, never by weakening a check.

The project's profile decides what happens to them ([AGENTS.md](../AGENTS.md) rules 15 and 24). This project is a `prototype`, so it accepts them all (decision 28). As `production` it would apply each production fix, or record in `decisions.md` who accepts the risk; 12 and 13 are the prototype's own and would no longer apply.

| # | Risk | Why it's a risk | Production fix |
|:-:|------|-----------------|----------------|
| 1 | The agent shares the developer's GitHub identity | It runs `gh` with the developer's token, so it could approve its own deploy, edit the apply environments or delete the ruleset; only `AGENTS.md` rules 20 and 21 ask it not to | Peer review: the `main` ruleset requires one approval from someone other than the author, and the apply environments turn on *Prevent self-review*, so the agent can't merge or deploy alone. This project's `scripts/protect-main.sh` sets only the prototype's ruleset (no approval needed); the second-reviewer mode is sdlc-template's `bash scripts/protect-main.sh production`, to be ported when the project becomes `production` |
| 2 | Pinned scanner and CI images go stale | The gitleaks, Trivy, Checkov, Semgrep, Infracost, Python and Node images are pinned by digest in `docker run` and `container:` lines, which Dependabot doesn't update, so the scanners age and miss newer checks | Renovate, which opens update PRs for those digests with the same 7-day wait; until then, update the pins by hand when changing a workflow |
| 3 | The deploy role is broad in places | `bedrock-agentcore:*` and `cognito-idp:*` are limited to the region and `cloudfront:*` to the account, not the project, because runtime, user pool and distribution ARNs use generated IDs, not names. In a shared account, the pipeline could change another workload's runtimes, user pools or distributions | A dedicated AWS account per project and environment, so there's nothing else in reach |
| 4 | A failing Terraform plan can merge | The `aws` workflow runs only when `infra/aws/`, the knowledge base's files or the workflow changes, so `plan` can't be a required check. The required `terraform` check validates every unit, so only an error that needs AWS to find gets through, and a unit whose plan failed is never applied | A small job that always runs, fails only when a plan failed, and is a required check |
| 5 | A PR's checks cover only what it changes | To keep PRs fast, Gitleaks scans only the PR's commits, Semgrep reports only findings it adds, the app jobs run only for the apps it changes, and CodeQL skips docs-only PRs. A new scanner rule that matches older code fails only the run on `main` or the weekly run, which block nothing; and a file the `changes` job files under the wrong app skips that app's checks. Unknown paths, and a failed `changes` job, run everything | Get alerts for failed runs on `main` and the weekly scans, and fix them like a failed PR; review the `changes` job's paths when the repo's layout changes |
| 6 | Cost is a warning, not a gate | The cost comment flags a plan above `MONTHLY_COST_LIMIT` but doesn't block the merge, and it prices only what Terraform creates, so usage such as model tokens and data transfer shows as nothing | A required check that fails above the limit, plus AWS Budgets and Cost Anomaly Detection for actual spend |
| 7 | Tier 2 has no WAF and open api and copilot URLs | CloudFront has no web application firewall, and the api and copilot function URLs take requests from anyone, not only CloudFront; every route still checks its token or key (the context's URL takes only its gateway's IAM-signed calls), but floods and probing reach the functions | AWS WAF on each distribution, and function URLs that only CloudFront can call (an origin access control with IAM auth) |
| 8 | Nothing enforces the agent's rules on the machine | It runs with the developer's files and credentials, so only `AGENTS.md` rules 20 and 21 stop it reading `.env` files and secrets, skipping a hook or changing cloud resources | Deny rules in the agent's own settings (Claude Code: `.claude/settings.json`) or a sandbox, covering `.env*` (except `.env.example`), `*.tfvars`, `git push --no-verify`, `terraform apply` and `aws`; secrets in a vault, not in local files |
| 9 | Plans run unreviewed code and are kept as files | The `plan` job runs a PR's Terraform with the read-only role before anyone reviews it, so a PR can read the state; and the saved plan holds state values in plain text, downloadable for a day by anyone who can read the repo | A private repo, a required reviewer on the plan environments, and plans encrypted before upload |
| 10 | Some checks are missing | The workflows aren't linted, though agents edit them; the report scripts that write the PR summaries have no tests or type checks; Terraform is validated but not linted; model evals run by hand from the console, with no CI job; and no automated accessibility check | actionlint or zizmor, and tflint, from pinned images as required checks; tests for the scripts; an evals job on the tiny sets with a spending limit; axe in the browser tests |
| 11 | CodeQL needs a paid plan on private repos | Code scanning with CodeQL is free on public repos only; on a private repo without GitHub Code Security the `codeql` workflow skips itself, so Semgrep is the only static analysis | Buy GitHub Code Security, or accept Semgrep alone and record it in `decisions.md` |
| 12 | A prototype runs without human gates | Nobody but the owner approves its plans, merges or `dev` deploys, and the agent settles unclear points itself (`AGENTS.md` rule 24), so a wrong design or a bad change is live in `dev` before a second person looks; the scans and required checks are the only gate | The `production` profile, with the second reviewer in 1 |
| 13 | A prototype is tested and reviewed lightly | New features get their main path and anything touching auth, money or personal data tested, with one review per branch; the 2026-11-11 feature pass was checked by hand and had no per-phase review, so edge cases and regressions surface late | Before it becomes `production`: abuse-case tests for every feature, a review in every phase, and the threat model re-approved |
