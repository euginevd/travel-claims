# Decisions

Key decisions only, newest last, each with why and what it replaced. Never delete one; add a new one that supersedes it.

1. **Rebuild UnderCover fresh, with credit** (2026-11-08). Why: the original repo has no licence, so publishing a copy of it isn't ours to do; its final version is the reference for behaviour and data. Instead of: forking the original repo.
2. **Local first, then AWS, then publish** (2026-11-08). Why: the whole app is proven on a laptop with a Claude API key before anything costs AWS money (spec 4–5). Instead of: building straight onto AWS.
3. **Anthropic API locally, Bedrock on AWS** (2026-11-08). Why: the API key is the quickest way to test, and tier 1 sends only made-up data; Bedrock's Australian inference profile keeps real claim data in Australia from tier 2 (spec 26). One module per app switches between them. Instead of: Bedrock from day one, or OpenRouter as in the original.
4. **The agent decides; code pays** (2026-11-08). Why: a model can be talked into a wrong answer, so limits and payments are enforced where no prompt can reach (spec 20). Instead of: letting the agent call the payment API.
5. **PostgreSQL in every stage** (2026-11-08). Why: the agent's saved progress, its memory and the records all need it, and Docker locally matches Aurora on AWS. Instead of: Supabase as in the original, SQLite, or DynamoDB.
6. **Containers from stage 1, EKS in stage 2** (2026-11-08). Why: the same images run in Docker Compose and on EKS, which inherits an enterprise platform's controls (GitOps, admission control, network policy) and controls the agent's egress. Instead of: AgentCore Runtime, simpler and right for smaller teams, or Lambda.
7. **Approval limit $1,000** (2026-11-08). Why: most claims are small and clear-cut; larger ones need a handler's sign-off (features 13). Instead of: a handler signing off every claim.
8. **Free security tools in the repo** (2026-11-08). Why: the public repo can't use a licensed Wiz tenant; the DevSecOps notes map where Wiz would replace each tool. Instead of: Wiz in the pipeline.
9. **Python 3.14, not 3.15** (2026-11-08). Why: LangGraph depends on `zstandard`, which has no 3.15 build yet; code-standards 15 asks for the current stable version, so move up once it does. Instead of: Python 3.15.
10. **Separate apps and identities for customers and staff** (2026-11-08). Why: a customer token must fail the staff API's signature and audience checks before any role check runs, so one bug can't expose the queue or payments; in tier 2 the staff app sits behind its own Cognito user pool and allowed networks. Instead of: one web app with two sign-ins and a role claim.
11. **UnderCover has its own brand design system** (2026-11-08). Why: a travel insurer's customers expect a bright, reassuring travel brand, so "Sky and sunset" (navy, sky blue, coral, Plus Jakarta Sans) replaces the restrained consultancy look; ArcVault stays the base for other projects. Instead of: ArcVault tokens.
12. **A separate console and identity for AI engineers** (2026-11-09). Why: evaluations, improvement rounds and the red team change how the agent behaves, so they sit in their own app (port 5175) behind a third issuer and audience, apart from the handlers' workspace, as OWASP's admin-interface guidance and NIST 800-53 SC-2 ask; the handlers' dashboard keeps only claims work. Instead of: hiding those pages from handlers by role in one dashboard.
13. **Serverless on AWS with Supabase in tier 2; EKS in tier 3** (2026-11-09). Supersedes 6, and 5's Aurora. Why: EKS, its nodes and NAT cost about $215–290 a month even idle, while the demo needs almost nothing running between uses. So, as in the original, the front ends go on S3 and CloudFront, `api`, `context` and `copilot` on Lambda, `agent` on AgentCore Runtime, and PostgreSQL on Supabase in Singapore (`ap-southeast-1`; Sydney wasn't offered, and the data is made up), for close to $0 idle plus Bedrock tokens; real claim data would need a database in Australia. The EKS design becomes tier 3, the enterprise build, done later at work. Instead of: EKS with Aurora (decisions 5 and 6), or one server running Docker Compose.
14. **Deployment tiers, not stages** (2026-11-09). Why: the three are ways to run the same apps side by side, and "stage" clashed with CI stages, a staging environment and the bootstrap's `Target`. So: tier 1 local (Docker), tier 2 AWS cost-optimised (serverless), tier 3 AWS enterprise pattern (EKS); `dev` and `prod` stay environments within a tier. Decision 6 keeps its old wording.
15. **A switch for Claude on AWS; the Anthropic API in `dev` first** (2026-11-10). Narrows 3 to `prod`. Why: the account has Anthropic credits, Claude's tokens are tier 2's main cost and cost the same on either, and `dev` holds only made-up data; Bedrock follows once the AWS build works. The `MODEL_PROVIDER` repository variable switches only Claude's calls; the guardrail, AgentCore and the Knowledge Base are AWS services either way. Instead of: Bedrock only from tier 2.
16. **Heartbeats, not a job queue, for claims the agent stops working** (2026-11-10). Why: the agent already saves every step on the claim's thread, so a stalled claim only needs noticing and handing back; a 20-second heartbeat with a 90-second limit does that with one column, and the same Retry works on AgentCore Runtime, where no process lives to notice. Instead of: a queue such as SQS with visibility timeouts, or leaving the claim `in_progress` (#57).
17. **Tier 2's AgentCore build, and what waits** (2026-11-10). Gateway fronts only the context layer, since the api's agent routes are claim-scoped by the agent's code and as Gateway tools the model would choose the claim (R3); Identity waits with them. Memory is records the agent writes itself, one namespace per customer, with no extraction strategy, so no model reads customers' words into memory (R20). The Knowledge Base holds the policy wording only, one document per section, for Ask UnderCover, which falls back to the context's word search. Code execution with MCP is built but off: its sandbox's public network could let a steered program send out what the model has read (R24), so it waits for a VPC-mode interpreter and an evaluation, a tier 3 nice-to-have. Instead of: every route through Gateway, extraction strategies over conversations, chunking the whole wording, or code execution on now.
18. **No Gateway policy on payments** (2026-11-10). Why: the original build lets the model call `pay_claim` as a tool, so a Gateway policy has something to stop; here the model can't reach a payment at all, since code pays in the graph's `pay` step after the `api` checks the limit and the kill switch (decision 4, R2, R21). Instead of: copying the original's policy, which would guard a door this design doesn't have.
19. **The judge runs in the agent service and is shown, never a gate** (2026-11-10). Why: every model call already goes through the agent's one model module (code-standards 4), so the `api` needs no Claude key or Bedrock permissions; the `api` sends one run's pairs (decisions, sections and reasons only), and the agent keeps and logs none of it (spec 24, R26). A grade is a model's opinion that hidden instructions could sway, so it informs AI engineers but never keeps a version, decides or pays. Instead of: the judge in the `api`, or the grade in the keep-or-roll-back rule.
20. **Senior handlers dispatch the live queue** (2026-11-10). Why: a dispatch spends money and decides claims in bulk, so it sits with the people who sign off large payouts and hold the kill switch (decision 7); it reuses the evaluations' dispatcher and `start_claim`'s compare-and-set, so it adds no new way to start or pay a claim (R25). Instead of: any handler starting one, or a separate job queue.
21. **The Canopy design system** (2026-11-11). Supersedes 11's "Sky and sunset". Why: the apps are shown to clients and employers, and the navy and sky look read as generic; Canopy is quieter and premium: white pages, faint glows, Newsreader headlines, a coral accent, double-ring cards and one near-black primary button a view (`design-system.md`). Instead of: restyling the old tokens.
22. **A senior handler changes the limits alone, on the record** (2026-11-11). Why: the head of claims operations owns the approval limit (business 7), the original lets senior handlers set it, and a demo needs it changed in one step; the range is fixed in code ($100 to $5,000), every change keeps who, when, old, new and why, a held payout stays held and a paid claim never changes (R27). Production would add a second approver. Instead of: a limit only in seed data, or a two-person change now.
23. **Success criteria in code** (2026-11-11). Why: whether the pilot meets its targets is a fact about scores and payments, so the `api` works it out and every screen and the Copilot repeat it; a model asked to judge it could be wrong or steered. Instead of: the Copilot or the explainer judging it.
24. **The Copilot acts only on a confirm card, and remembers preferences only** (2026-11-11). Why: a dispatch spends money and a send-back changes a claim, so each waits on the same card as a sign-off, and a sign-off answer can't confirm another action; memory is the handler's own notes, from their verified sign-in, so no customer's words are carried between conversations (R28). Instead of: the original's direct tool calls, or extraction over conversations.
25. **Live disagreements feed the evaluation set, never the held-out set** (2026-11-11). Why: a handler overriding the agent is the best new test there is, and evaluation tools all close this loop; an engineer adds each one by hand, a claim the hidden-instruction check flagged is refused, and the held-out set stays untouched so it still measures what the improver hasn't seen (R29). Added claims aren't in the five-claim tiny sets yet, so rounds don't use them. Instead of: adding them automatically, or leaving production out of the tests.
26. **Precedents and live figures in code, tracing in the console** (2026-11-11). Why: similar claims and the Live page are counts and comparisons over records the `api` already holds, so they cost nothing and can't be steered; the console's Claim trace already shows every step, call and cent, so a self-hosted tracing stack (four or five more containers) waits for a need. Instead of: embeddings for similarity, or Langfuse in tier 1.
27. **Tier names say what each runs on** (2026-11-11). Refines 14. So: tier 1 local (Docker), built; tier 2 AWS serverless, cost-optimised, built; tier 3 AWS enterprise (EKS, private network), designed, not built. Why: "tier" alone can read as a quality ranking, and "scalable" for tier 3 would suggest serverless doesn't scale; what tier 3 adds is control: private subnets, a firewall, a multi-zone database in Australia and admission rules. Three are kept because knowing when serverless stops being enough is part of what the project shows. Instead of: two tiers, or "enterprise scalable pattern".
28. **Profile: prototype; every trade-off accepted; one owner** (2026-11-11). Why: the project is a demonstration for clients, employers and recruiters with made-up data, no real users and simulated payments, so speed matters more than gates; the template it grew from (sdlc-template) now names this a `prototype` (AGENTS.md rule 24). Eugine owns the code and accepts all thirteen trade-offs in [guides/04-security-trade-offs.md](../guides/04-security-trade-offs.md). Kept above the prototype's minimum because they already exist: the threat model, 80% coverage and the security scans. To become `production`: `Profile` changes in `spec.md` with a new decision, the threat model and costs are re-approved, the skipped abuse-case tests are added, each trade-off gets its fix or a named acceptor, a second reviewer is set on `main` (by porting sdlc-template's `protect-main.sh production` mode, which this project's script lacks, then running it) and on the apply environments, and real data moves to a database in Australia. Instead of: holding a demo to production's approvals.
29. **Two tiers; tier 2's secure target replaces tier 3** (2026-11-11). Supersedes 6's and 13's EKS, and refines 27. So: tier 1 local (Docker); tier 2 AWS serverless, as built (cost-optimised, Supabase and the Anthropic API outside AWS, made-up data only) and a planned secure target, to build and then test (AWS-native: Aurora in Sydney, Claude on Bedrock only through PrivateLink, private subnets and VPC endpoints, WAF, a Control Tower landing zone, GuardDuty and Security Hub). Why: EKS would add control this app gets more cheaply by hardening what's built; AWS's own pattern for agentic apps is managed and serverless (AgentCore, Lambda, Bedrock); a handful of bursty services doesn't need a cluster or a platform team; and about $100 to $200 a month beats about $400. Instead of: tier 3 on EKS.
30. **Tier 2 fully AWS-native, at close to $0 idle** (2026-11-11). Refines 29. So: no VPC, NAT gateway or VPC endpoints; Aurora DSQL (IAM sign-in, scales to zero) replaces Supabase, DynamoDB holds the agent's checkpoints, Claude is on Bedrock only, and anything that costs money just by existing is swapped for a free alternative: the CloudFront flat-rate Free plan (WAF and DDoS protection) on the three apps' sites, with the static project page on Shield Standard alone; CloudWatch alarms within the free tier, SNS email, an AWS Budgets alert, IAM Access Analyzer and CloudTrail's free 90-day event history for audit. The app secret moves from Secrets Manager to a free SSM Parameter Store SecureString. On DSQL the schema is built once from the models and stamped as the newest migration, since DSQL takes one schema change per transaction and only asynchronous indexes; a lost write race is a 409, never retried by the server, so a payout can't run twice. The agent's and the Copilot's checkpoints are compressed in DynamoDB without S3 offload, and expire after a week; the Copilot's conversations and handlers' notes are in their own DynamoDB table. The api's role may sign in to any DSQL cluster in the account as admin (it holds only this one); a role per cluster and app is the paid-path follow-up. Claude starts on the Anthropic API in `dev` (`MODEL_PROVIDER=anthropic`, the key a GitHub secret on the apply environment that the secrets unit writes into the settings and removes on a switch to Bedrock), with Bedrock to test after; real data would take Bedrock only (spec 26). `dev` is the only environment: the bootstrap, workflow and units have no `prod` (decision 28 says what production adds). Not built, as each would cost or fail on a new account: Lambda reserved concurrency (new accounts have only ten) and an alarm on the payout switch (a custom metric). The bootstrap grants the paid options too, so turning one on later needs no bootstrap change, but the pipeline can't approve a paid CloudFront plan. More secure, paid, and added before real data: a paid WAF web ACL or plan, GuardDuty, Security Hub and AWS Config, a CloudTrail trail to a locked bucket, customer-managed KMS keys, a VPC with PrivateLink to Bedrock, a DSQL role per app in place of admin, and a Control Tower landing zone. Why: the demo needs almost nothing running between uses, every piece is managed and scales without a change, and about $100 to $200 a month buys protections made-up data doesn't need. Instead of: decision 29's secure target as planned.
31. **The whole project is a prototype, in `dev` only** (2026-11-11). Refines 28. So: no `prod` target, parameter, branch or setting anywhere in its code, workflows or infrastructure, and every `dev` resource tears down cleanly. Why: the project is a demonstration on made-up data; a real service would be a new decision, and decision 28's path to `production` and decision 30's paid options say what it would add. Instead of: keeping `prod` wired in, unused.
32. **A wide bootstrap while building, narrowed at the end, for a prototype only** (2026-11-11). Refines 30. So: the bootstrap grants every Bedrock and AgentCore feature (guardrails, knowledge bases, evaluations, prompts, flows, agents, batch, Identity, Browser), AWS's AI services (Textract, Comprehend, Translate, Rekognition, Transcribe, Polly, Kendra, OpenSearch Serverless), the workflow services (SQS, Step Functions, EventBridge Scheduler, API Gateway, Cognito identity pools) and AgentCore Identity's secrets, limited to `ap-southeast-2` or to `travel-claims-*` names, and its boundary caps the app roles at the same. The pipeline can't buy commitments: Bedrock provisioned throughput, Marketplace subscriptions and a paid CloudFront plan are denied. Why: the stack is deployed once, by hand, and new AI features shouldn't wait on a change to it; each role Terraform makes still has its own narrow policy. Then: once every feature is built and deployed, a permissions audit (TODO) narrows the deploy role, plan role and boundary to what CloudTrail shows is called, and drops the Checkov skips for the width. Only because the project is a prototype on made-up data (decision 31): `production` starts at least privilege and adds each service by a reviewed bootstrap change. Instead of: least privilege from the start, with a bootstrap update for each new service.
33. **Agent identity through AgentCore Identity on AWS** (2026-11-12). Refines 30. So: each app that fetches credentials has a workload identity (`api`, `agent`, `copilot`); the Anthropic key is an API key credential provider in the token vault, which only the agent's and Copilot's identities fetch, not a value in the shared settings; the agent's runtime takes only the api's machine token (a Cognito client-credentials token from a services pool, scoped to `undercover-agent/invoke`), which AgentCore Identity fetches so the api never holds the client's secret; and the Copilot reaches the context tools through a second gateway that checks the handler's own ID token and lets in only the `handlers` group, so each lookup is tied to a person. The agent and lookup programs keep the IAM-signed gateway, as one gateway takes one kind of sign-in. Locally nothing changes: Docker keeps the agent's key and direct calls. Still shared: the agent's key on its calls back to the api. Why: no long-lived shared secret between the api and the runtime, the model key readable only by the apps that use it, and tool calls attributable to a handler. Cost: Identity is free through Runtime and Gateway and $0.010 per 1,000 requests from Lambda; Cognito's machine tokens are about $0.00225 each (the US East rate), reused for 50 minutes. Instead of: IAM-signed calls and the key in the settings.
34. **Tool rules, no context URL, and a model-call audit trail** (2026-11-12). Refines 33. So: both gateways invoke the context server by its ARN (Lambda targets, the Lambda Web Adapter passing each call to `/events`), so it has no URL; one AgentCore Policy engine, in ENFORCE mode, permits the agent's gateway all seven lookups and the Copilot's only `search_documents` and `read_section`, denying anything else; and Bedrock model invocation logging keeps every Bedrock call's text for 30 days in a private bucket whose objects only the deploy role can delete. Payment limits stay in the api, as payments aren't gateway tools. Why: a public URL fewer, tool rules the model can't talk its way past, and a record of each AI decision, for free or cents. Cost: Policy $0.000025 per check; logs a few cents of S3. Instead of: an IAM-only context URL, any tool for any gateway caller, and no record of model calls.
35. **Account-wide settings in their own unit, skipped where a platform team runs them** (2026-11-12). Refines 30 and 34. So: the budget alert and IAM Access Analyzer move from `monitoring` to a `platform` unit, applied last; `PLATFORM_MANAGED=true` makes the workflow and `deploy-aws.sh` skip it. The workload's own alarms and Bedrock model invocation logging, an audit trail of its own AI decisions, stay in `monitoring`; the logging setting is one per account and Region, so in a shared account the workload agrees it with the platform team. Everything else a platform owns is already a setting: the workflows only read the role ARNs and state bucket the bootstrap outputs, the api's token issuer, audience and group are settings, and `CLOUDFRONT_FREE_PLAN=false` drops the plan and its WAF. Why: a regulated insurer's platform team already runs these for every workload, and a workload that set them would overwrite the platform's. Instead of: the workload owning account-wide settings.
36. **A private network by default, public by setting** (2026-11-12). Refines 30 and 35. So: the `api`, `context` and `copilot` Lambdas, AgentCore Runtime and Code Interpreter run in private subnets in two availability zones, reaching AWS through VPC endpoints (ECR, Logs, SSM, Bedrock's runtime and knowledge bases, AgentCore and its gateways, and free gateway endpoints for S3 and DynamoDB) and anything else (the apps' function URLs, Cognito's signing keys, DSQL, the Anthropic API) through one NAT gateway, standing in for a platform's central, inspected egress. The network is the `platform` unit's, as a landing zone would provide it, and the workload finds it through the `/platform/network/vpc-id` and `/platform/network/private-subnet-ids` parameters, the same contract a real platform publishes; so the `platform` unit now applies first and destroys last. The workload owns its security groups: out only on HTTPS and PostgreSQL, nothing in; lookup programs reach only the endpoints, never the internet (R24). `NETWORK_MODE=public` builds no network and runs everything as decision 30 did. The bootstrap gains the network actions, limited to the region, and the boundary lets Lambda make its network interfaces. Why: the repo shows the design a regulated insurer runs, and cost is a choice made at deploy time, not in the design. Cost: about $150 to $200 a month while up (eight interface endpoints in two zones and one NAT gateway: about $150 at US East rates, more in Sydney), $0 on public. Instead of: no VPC (decision 30), or a VPC in each workload unit.
37. **One enterprise design; Docker only for local tests** (2026-11-12). Supersedes the tiers of 14, 27 and 29. So: no tiers. The repo holds one design, the AWS build in `infra/aws/`, which a regulated insurer would run with its platform team's controls in place (the architecture guide), deployed here to `dev` on made-up data; Docker Compose runs the same apps on a laptop for a quick test before deploying. Why: tiers read as two products, and the cheaper one as the design; cost is now a deploy-time setting (decision 36). Instead of: tier 1 local and tier 2 AWS.
38. **The enterprise gaps closed, each where it belongs** (2026-11-12). Refines 33, 34, 35 and 36. Workload: DSQL through its own PrivateLink endpoint (its hostname is `<cluster>.<service id>.<region>.on.aws`), so the api's connections never leave the network, and the functions' PostgreSQL rule reaches only the VPC; two more Bedrock guardrails check the model's output, failing closed: a grounding check on Ask UnderCover's answers against what its tools returned, and a filter on letters and drafts for card, bank, tax file and passport numbers (names, emails and phones stay with the handler who reads the letter); the agent's calls back to the api carry a machine token from AgentCore Identity (a services-pool client scoped `undercover-api/agent`), and with it set the api refuses the shared key, so none is used on AWS; the agent sends its traces with AWS Distro for OpenTelemetry, and AgentCore Evaluations scores `EVALUATION_SAMPLING` per cent (default 10) of live sessions with built-in judges. Platform: AWS Backup (a vault, a daily plan kept 7 days, and a selection by the tag `Backup=daily`, which the DSQL cluster carries, as an organization backup policy selects), and CloudWatch Transaction Search, one setting per account, which sends spans to `aws/spans` for Observability and Evaluations. The bootstrap gains Backup, the evaluation role's reads and passing a role to Backup. Why: each gap the architecture guide listed is a control a regulated insurer expects, and each sits with its owner, so a platform team replaces only its own part. Cost: the DSQL endpoint about $15 to $20 a month while up; backups, traces and evaluations cents to dollars in use. Instead of: listing them as gaps.
39. **Every control in code, each deployed by a setting** (2026-11-12). Refines 36 and 38. So: the repo holds the whole enterprise design as code, and whether a piece is deployed is a setting chosen for its cost, never a missing file. Added under it: `API_GATEWAY=true` puts the api and Copilot behind an API Gateway HTTP API whose JWT authorizers check each audience's Cognito token (the agent's scoped access token on `/api/agent/*`), with throttling and access logs, and removes their function URLs, so nothing reaches the functions except through it (trade-off 7); off by default. `STAFF_SAML_METADATA_URL` and `STAFF_SIGN_IN_URLS` sign handlers and AI engineers in with the company's IAM Identity Center, assumed in place, federated into their Cognito pools by SAML, with a sign-in trigger copying Identity Center groups into the groups the api checks; off by default. Settings stay split: names and IDs in Parameter Store, secrets in Secrets Manager (the token vault keeps the Anthropic key and both machine clients' secrets there), and no shared agent key on AWS. Why: a reviewer sees the full design in code, and a `dev` account pays only for what's switched on. Cost: API Gateway about $1 per million requests; Identity Center free. The defaults are the cost-optimized ones (`NETWORK_MODE=public`, `EVALUATION_SAMPLING=0`, `API_GATEWAY=false`), refining decision 36's private default, and the architecture guide names the recommended value of each. Instead of: leaving pieces out to save cost, or a REST API (chosen where WAF on the API or a private API is needed).
40. **The platform's pieces are assumed; its code is reference** (2026-11-12). Supersedes 35's `PLATFORM_MANAGED`. So: a platform team is assumed to run the account, so the `platform` unit (network, backups, Transaction Search, budget alert, Access Analyzer) is reference code the pipeline skips; `DEPLOY_PLATFORM=true` deploys it in an account with no platform team, such as a personal demo account, and `NETWORK_MODE=private` and online evaluations need it there. Why: the workload's design shouldn't build what an enterprise account already has; the code stays to show what the workload relies on. Instead of: building the platform's pieces unless told not to.
41. **The workload consumes the platform; it doesn't build it** (2026-11-12). Supersedes 40, and 35's and 38's platform pieces. So: the `platform` unit and `DEPLOY_PLATFORM` are gone. The workload reads `/platform/network/vpc-id` and `/platform/network/private-subnet-ids` with `NETWORK_MODE=private`, tags its DSQL cluster `Backup=daily` for the platform's backup policy, relies on the platform's Transaction Search for traces and online evaluations, and on its Firewall Manager with `CLOUDFRONT_FREE_PLAN=false`; the budget alert and Access Analyzer are the platform's too, so `MONTHLY_BUDGET` is gone. The bootstrap keeps only the workload's side: security groups, DSQL's endpoint and reading `/platform/*`. Staff federation with IAM Identity Center stays as reference code (the identity unit and the api's check), never switched on, and the apps' sign-in pages don't change. The architecture guide lists what the workload expects from the platform. Why: building the platform's pieces in a workload repo blurs who owns them. Instead of: reference code for the platform in this repo.
42. **Review fixes before the first deploy** (2026-11-12). Refines 33, 38 and 39. So: the machine clients' secrets are kept in AgentCore Identity's vault but also sit in the identity unit's Terraform state, accepted for the prototype as trade-off 14 rather than "no secret in state"; machine tokens are reused until five minutes before they expire and refreshed once on a 401; a failed vault call at the agent's start is logged, not fatal; the api's timeout is 60 seconds, as its first start builds DSQL's schema; the agent may fetch only its own workload token, and the Copilot only the Anthropic key's provider; the teardown script deletes only this project's buckets and the uploaded bootstrap template. Why: the branch review found them. Instead of: deploying first.
43. **API Gateway as a REST API with its own WAF** (2026-11-12). Supersedes 39's HTTP API. So: with `API_GATEWAY=true`, a regional REST API carries a WAF of its own (AWS's common, known-bad-input and IP-reputation rules and a rate limit per IP), so the rules apply to every call, including one that skips CloudFront and the agent's and Copilot's own calls; Cognito authorizers check each audience's token, the agent's with its scope; throttling and access logs at the stage (whose logging role is the platform's account setting). Why: an HTTP API can't carry a WAF, so a caller who skipped CloudFront skipped its rules, and a private API can't sit behind CloudFront. Cost: about $3.50 per million requests and $10 a month for the WAF. Still off by default and not deployed here. Instead of: the HTTP API with JWT authorizers.
44. **Staff sign in with the company's Okta** (2026-11-12). Refines 39 and 41. So: the staff and engineering pools federate with Okta by SAML (an Okta SAML app sending `email` and a group attribute statement with the person's group names), in place of IAM Identity Center; Identity Center stays the platform's, for people's access to AWS itself. Still reference code, never switched on here, and the apps' sign-in pages don't change. Why: a regulated insurer usually connects its business apps straight to its corporate identity provider, and keeps Identity Center for AWS access. Instead of: IAM Identity Center as the apps' identity provider.
45. **Six more common enterprise patterns, each a setting** (2026-11-12). Refines 39 and 41. So: `ENCRYPTION_KEYS=platform` puts the platform's KMS data key (from `/platform/kms/data-key-arn`) on DSQL, both DynamoDB tables, the receipts bucket, the settings parameter (which `fill-secret.py` keeps under that key on every write) and the functions' logs, and each role may use it only through those services; `DOMAIN_NAME` serves the project page at the company's domain and each app under it, with ACM certificates validated in the zone the platform delegates; the DynamoDB tables and the receipts bucket carry `Backup=daily` like DSQL; `MALWARE_SCANNING=true` has GuardDuty scan and tag each receipt, and the bucket serves only receipts tagged clean; `LOG_MASKING=true` masks emails, card details and AWS secret keys in the functions' logs; `DATABASE_APP_ROLE=true` has the api serve requests through a DSQL role that can only read and write its tables (the schema build at each cold start still signs in as admin, so the IAM role keeps `DbConnectAdmin`; a separate schema job would drop it). All off by default and not deployed here. Why: they're the patterns a regulated insurer's security review asks for first, each small and common. Cost: cents to a few dollars a month each when on. Instead of: leaving them as gaps.
46. **A read-only troubleshoot role in the bootstrap** (2026-11-12). Refines 32.
