# Decisions

The decisions in force, newest last: what, why, and what it replaced. A superseded decision keeps its number as a one-line pointer, so citations still work; git keeps the full text. To change one, add a new decision and shorten the old one to a pointer.

1. **Rebuild UnderCover fresh, with credit** (2026-11-08). Why: the original repo has no licence; its final version is the reference for behaviour and data. Instead of: a fork.
2. **Local first, then AWS** (2026-11-08). Why: prove the app on a laptop before it costs AWS money (spec 4–5). Instead of: building straight onto AWS.
3. **Anthropic API locally, Claude on AWS by switch** (2026-11-08). One module per app picks the provider; decision 15 sets AWS's. Why: an API key is quickest to test; Bedrock in Sydney keeps real data in Australia (spec 26). Instead of: OpenRouter, as in the original.
4. **The agent decides; code pays** (2026-11-08). Why: a model can be talked into a wrong answer, so limits and payments sit where no prompt reaches (spec 20). Instead of: the agent calling the payment API.
5. *Superseded by 30:* PostgreSQL locally, Aurora DSQL on AWS.
6. *Superseded by 37:* containers on EKS.
7. **Approval limit $1,000** (2026-11-08). Larger claims need a handler's sign-off (features 13). Why: most claims are small and clear-cut. Instead of: signing off every claim.
8. **Free security tools in the repo** (2026-11-08). Why: a public repo can't use a licensed Wiz tenant. Instead of: Wiz in the pipeline.
9. **Python 3.14, not 3.15** (2026-11-08). Why: LangGraph needs `zstandard`, which has no 3.15 build; move up once it does. Instead of: Python 3.15.
10. **Separate apps and identities for customers and staff** (2026-11-08). Why: a customer token fails the staff API's signature and audience checks before any role check, so one bug can't expose the queue or payments. Instead of: one app with a role claim.
11. *Superseded by 21:* the "Sky and sunset" design system.
12. **A separate console and identity for AI engineers** (2026-11-09). Evals, improvement and the red team live in their own app (port 5175) with a third issuer. Why: they change the agent's behaviour, so they sit apart from claims work (OWASP admin guidance, NIST SC-2). Instead of: hiding pages by role.
13. *Superseded by 30 and 37:* serverless with Supabase, EKS as tier 3.
14. *Superseded by 37:* deployment tiers.
15. **`MODEL_PROVIDER` switches Claude on AWS; the Anthropic API in `dev` first** (2026-11-10). Only Claude's calls switch; guardrails, AgentCore and the Knowledge Base are AWS either way. Why: Anthropic credits and made-up data in `dev`; real data takes Bedrock only. Instead of: Bedrock only.
16. **Heartbeats, not a job queue, for stalled claims** (2026-11-10). A 20-second heartbeat with a 90-second limit hands a stalled claim back for Retry. Why: the agent already saves every step, so a stall only needs noticing, and it works on AgentCore Runtime too (#57). Instead of: SQS visibility timeouts.
17. **AgentCore's scope** (2026-11-10). Memory holds records the agent writes, one namespace per customer, with no extraction (R20); the Knowledge Base holds the policy wording, one document per section; code execution with MCP is built but off until a VPC-mode interpreter (R24). Why: no model reads customers' words into memory, and a sandbox with public network could leak. Instead of: extraction strategies, or code execution on.
18. **No Gateway policy on payments** (2026-11-10). Why: the model can't reach a payment; code pays after the api checks the limit and kill switch (decision 4, R2, R21). Instead of: copying the original's policy.
19. **The judge runs in the agent service and is shown, never a gate** (2026-11-10). Why: every model call goes through the agent's one model module, and a grade can be swayed, so it informs but never keeps a version or pays (spec 24, R26). Instead of: the judge in the api, or in the keep-or-roll-back rule.
20. **Senior handlers dispatch the live queue** (2026-11-10). Why: a dispatch decides claims in bulk, so it sits with whoever holds the kill switch; it reuses `start_claim`'s compare-and-set (R25). Instead of: any handler, or a job queue.
21. **The Canopy design system** (2026-11-11). White pages, Newsreader headlines, a coral accent, one near-black primary button a view (`design-system.md`). Why: the apps are shown to clients and employers, and the old look read as generic. Instead of: "Sky and sunset" (11).
22. **A senior handler changes the limits alone, on the record** (2026-11-11). The range is fixed in code ($100 to $5,000); each change records who, when, old, new and why (R27). Why: a demo needs it in one step; production would add a second approver. Instead of: a two-person change.
23. **Success criteria in code** (2026-11-11). Why: whether the pilot meets its targets is a fact about scores and payments; a model judging it could be wrong or steered. Instead of: the Copilot judging it.
24. **The Copilot acts only on a confirm card, and remembers preferences only** (2026-11-11). Why: dispatches and send-backs change claims, so each waits on a card; memory is the handler's own notes, never a customer's words (R28). Instead of: direct tool calls, or extraction over conversations.
25. **Live disagreements feed the evaluation set, never the held-out set** (2026-11-11). An engineer adds each by hand; flagged claims are refused (R29). Why: an override is the best new test, and the held-out set must stay unseen. Instead of: adding them automatically.
26. **Precedents and live figures in code, tracing in the console** (2026-11-11). Why: counts over records the api holds cost nothing and can't be steered; the Claim trace already shows every step and cent. Instead of: embeddings, or Langfuse.
27. *Superseded by 37:* tier names.
28. **Profile: prototype; every trade-off accepted; one owner** (2026-11-11). Eugine owns the code and accepts every trade-off in guide 04; the threat model, 80% coverage and the scans stay. Why: a demonstration on made-up data, where speed matters more than gates. To become `production`: a new decision, the threat model and costs re-approved, abuse-case tests, a fix or named acceptor per trade-off, a second reviewer on `main` and the apply environments, and data in Australia.
29. *Superseded by 37:* two tiers.
30. **AWS-native serverless, close to $0 idle** (2026-11-11). Lambda and AgentCore Runtime, Aurora DSQL (IAM sign-in, built once from the models), DynamoDB for checkpoints (a week), settings in an SSM SecureString, CloudWatch alarms and CloudTrail's free history. Why: the demo runs almost nothing between uses, and each piece scales without change. Instead of: EKS, Supabase or a paid secure target.
31. **The whole project is a prototype, in `dev` only** (2026-11-11). No `prod` target, parameter, branch or setting anywhere, and `dev` tears down cleanly. Why: a real service would be a new decision (28). Instead of: `prod` wired in, unused.
32. **A wide bootstrap while building, for a prototype only** (2026-11-11). It grants Bedrock, AgentCore, AWS's AI and workflow services, limited to `ap-southeast-2` or `travel-claims-*`, with commitments denied; a permissions audit (TODO) narrows it once built. Why: new AI features shouldn't wait on a bootstrap change. Instead of: least privilege from the start, which production keeps.
33. **Agent identity through AgentCore Identity** (2026-11-12). Each app has a workload identity; the Anthropic key is in the token vault, readable only by the agent and Copilot; the api calls the runtime with a Cognito machine token; the Copilot's gateway checks the handler's own token. Why: no long-lived shared secret, and tool calls tied to a person. Instead of: IAM-signed calls and the key in settings.
34. **Tool rules, no context URL, and a model-call audit trail** (2026-11-12). Gateways call the context server by ARN; an AgentCore Policy engine allows the agent all seven lookups and the Copilot two; Bedrock invocation logs are kept 30 days. Why: a URL fewer, tool rules the model can't argue past, and a record of each AI decision. Instead of: an IAM-only URL and no record.
35. *Superseded by 41:* a `platform` unit with `PLATFORM_MANAGED`.
36. **A private network by setting** (2026-11-12). `NETWORK_MODE=private` runs the functions and runtime in the platform's subnets (`/platform/network/*`) with VPC endpoints and egress on HTTPS and PostgreSQL only; `public`, the default since 39, builds no network. Why: the design shows what an insurer runs; cost is a deploy-time choice. Instead of: a VPC in each unit.
37. **One enterprise design; Docker only for local tests** (2026-11-12). The repo holds one AWS design in `infra/aws/`, deployed here to `dev`; Docker Compose runs the same apps locally. Why: tiers read as two products. Instead of: tiers (14, 27, 29).
38. **The enterprise gaps closed, each where it belongs** (2026-11-12). DSQL through PrivateLink when private; guardrails on output (grounding, and card, bank, tax and passport numbers); the agent calls the api with a machine token; ADOT traces; AgentCore Evaluations samples `EVALUATION_SAMPLING`%; `Backup=daily` tags. Why: controls an insurer expects, each with its owner. Instead of: listing them as gaps.
39. **Every control in code, each deployed by a setting** (2026-11-12). Whether a piece is deployed is a cost setting, never a missing file; defaults are the cheap ones (`NETWORK_MODE=public`, `EVALUATION_SAMPLING=0`, `API_GATEWAY=false`). Names in Parameter Store, secrets in Secrets Manager. Why: reviewers see the whole design, and `dev` pays only for what's on. Instead of: leaving pieces out.
40. *Superseded by 41:* platform code as reference.
41. **The workload consumes the platform; it doesn't build it** (2026-11-12). It reads `/platform/*` parameters for network, KMS, WAF and zones; Access Analyzer, Transaction Search and backups are the platform's; the account's budget alert is in the bootstrap (AGENTS.md rule 28, decision 54). The architecture guide lists what it expects. Why: building the platform's pieces blurs who owns them. Instead of: a `platform` unit.
42. **Review fixes before the first deploy** (2026-11-12). Machine-client secrets in Terraform state accepted as trade-off 14; tokens reused until five minutes before expiry; a failed vault call at start is logged, not fatal; api timeout 60 seconds; each app fetches only its own credentials; teardown deletes only this project's buckets. Why: the branch review found them. Instead of: deploying first.
43. **API Gateway as a REST API with its own WAF** (2026-11-12). With `API_GATEWAY=true`, a regional REST API with AWS managed rules, a rate limit, Cognito authorizers, throttling and access logs; off here. Why: an HTTP API can't carry a WAF, so callers skipping CloudFront skipped its rules. Instead of: an HTTP API.
44. **Staff sign in with the company's Okta** (2026-11-12). The staff and engineering pools federate with Okta by SAML, as reference code never switched on. Why: insurers connect business apps to their corporate identity provider and keep IAM Identity Center for AWS access. Instead of: Identity Center for the apps.
45. **Six enterprise patterns, each a setting** (2026-11-12). `ENCRYPTION_KEYS=platform`, `DOMAIN_NAME`, `Backup=daily` on tables and buckets, `MALWARE_SCANNING`, `LOG_MASKING` and `DATABASE_APP_ROLE`; all off here. Why: the first things an insurer's security review asks for. Instead of: leaving them as gaps.
46. **A read-only troubleshoot role in the bootstrap** (2026-11-12). `travel-claims-troubleshoot` has `ReadOnlyAccess`, assumed through a `travel-claims-cli` user allowed nothing else, for an hour at a time. Agents troubleshoot with it; a prototype may read secrets but never prints or sends them (AGENTS.md rule 26). Why: a diagnosis needs logs and state, and the developer's own credentials could change anything. Instead of: the developer's credentials.
47. **The Security section of the console** (2026-11-12). Posture answers "would we stop an attack?" from the latest red-team run against the version in use, the threat catalogue and controls that fired; each red-team run keeps the agent version it attacked. Why: figures worked out in code cost nothing and can't be steered. Decision 49 sets the console's order.
48. **Receipts read by Textract, answers checked by Automated Reasoning** (2026-11-12). Textract's `AnalyzeExpense` turns each receipt into text before any model sees it, falling back to the image marked unread; an Automated Reasoning policy from the wording checks Ask UnderCover's answers and holds back any it contradicts. Both stay in Sydney; neither runs locally. Why: no model reads an image a customer made, and answers must follow the wording. Instead of: grounding alone.
49. **The console leads with evals, in two sections** (2026-11-12). It opens on the Scoreboard; the top bar switches between Evals and Security. The improver never sees a held-out score, and engineers run only the practice set by hand. Why: evals are the core skill for its audience, and a held-out score fed back wears the exam out. Refines 47.
50. **Bedrock Data Automation as an option** (2026-11-12). `RECEIPT_READER` picks `textract` (the default), `data-automation` or `none`. Data Automation stays off until it runs an asynchronous project, since a synchronous one refuses the Receipt blueprint. Its Asia Pacific profile may process outside Australia, so real data keeps Textract. Instead of: Data Automation by default.
51. **CloudFront WAF on or off, from the platform's Firewall Manager** (2026-11-12). `CLOUDFRONT_WAF=off` (the default here) puts no WAF on the sites, which keep every security header; `on` tags each distribution for the platform's Firewall Manager policy (known mistake 45). Why: the Free plan refused this build's headers policy, and an insurer's WAF is the platform's. Instead of: the CloudFront Free plan, or a workload-built web ACL.
52. **Gates by profile, deploy early, one branch per session, short docs** (2026-11-13). `AGENTS.md` works by gates G0 to G5; cloud work starts with a walking skeleton; who says go to commit, push and merge is decision 56's; docs follow code standard 23's length rule, and this file keeps only decisions in force. Why: the first deploy needed 12 fix PRs (#87 to #98), the deploy target changed six times, and long docs were hard to read. Instead of: the old profile rule's exceptions, a PR per failure, and a full history here.
53. **The customer portal is a conversation** (2026-11-13). Wattle is the home screen, with an at-a-glance row of claims, cover and payouts; Messages, Claims and Settings open in one side panel. The model never acts: its reply names one action from a fixed list, code fills the card from the customer's own records, and only the customer's tap changes anything (threat R31). Why: customer first and minimal, one question at a time, without giving a model the power to act.
54. **Audit fixes: money limits in code, a budget alert, a quality gate** (2026-11-13). The AWS demo signs in only the plain test handler, never the senior one; an override pays at most what was claimed, within the plan's largest benefit; payments read the pause switch and approval limit locked; money is compared in cents; the bootstrap has the account's budget alert and no KMS key-tagging grants (the platform's key is used through a service-scoped grant); a manual `quality` workflow holds the agent to floors on the evaluation set and fails on any red-team attack not held; the browser tests run in CI on the Compose stack, with axe; the three web apps share sign-in, session, error and logo code in `packages/web-core`, and staff sign-in handles authenticator challenges by name, so MFA can be turned on without breaking it. Why: an end-to-end audit found each one. Instead of: trusting a passer-by with the senior handler, and floats for money.
55. **Brought back in line with sdlc-template where it moved ahead** (2026-11-13). From the template: the `workflows` job (actionlint, zizmor, shellcheck), the `kickoff` check, the report scripts' tests, `protect-main.sh production`, the budget's `BudgetEmail` and `MonthlyBudgetUsd` parameters (empty email, no budget), rule 10's note on new apps and known mistake 52. After the owner's yes, also its prototype autonomy (decision 56) and its `.claude/settings.json`, without the `.env` read denies a prototype drops; everything else here is ahead of it. Why: the owner asked for what's worth adding. Instead of: copying the template wholesale over a project that has moved on.
56. **A prototype commits, pushes, opens and merges its PR without asking** (2026-11-13). As sdlc-template now has it: within the limits in `AGENTS.md` rule 12, the agent decides what production would ask about, records it here and reports it; production still waits to be asked. `.claude/settings.json` enforces the floor (no force-push, `--no-verify`, `terraform apply`, ruleset edits or PR approvals) and turns off AI attribution lines (rule 29). Why: the owner chose the template's model. Replaces decision 52's "only when asked". Instead of: asking before each commit and push.
57. **The handlers' dashboard leads with the agent, and the agent waits to be switched on** (2026-11-13). Today replaces the queue page: Wattle's brief, figures to act on and the claims that need you, each with why; a claim opens on the agent's verdict and the one action it needs, the evidence in tabs. Any handler decides a referral within the approval limit (R32). A senior handler's switch turns the agent on for the live queue, replacing Dispatch; the demo starts with it off, so the queue can be watched as it works, and Settings resets the demo by ticks. Why: the portal's standard (one thing at a time) for the people who check the agent, and a demo that shows the agent working rather than its results.
58. **The console opens on whether the agent is fit to run** (2026-11-13). An Overview of five release gates replaces the Scoreboard as home, each judged in code with its likely range (watch when the range still reaches the target), beside the controls and what needs attention. Security gains an Agents map and an Audit log; the risk table moves to Posture. Why: an AI and security engineer's question is fit to run, on evidence, with the controls and the record in reach; the pages behind it stay the evidence.
59. **The console is an AI control plane** (2026-11-13). Renamed from the AI assurance console and organised by the field's four jobs: Observe, Evaluate, Secure, Govern, with the agent and payouts switches and an alerts bell on every page. It gains an output guard, a daily budget that switches the agent off, alerts and shadow tests. Why: vendors (Fiddler, Microsoft Agent 365, Openlayer) call this combination a control plane, and an engineer reviewing the project recognises it; each addition closes a gap from the industry's capability list, in code, with no new service.
60. **The audit log is a hash chain** (2026-11-13). Each entry is sealed once with a SHA-256 digest of what it says, chained to the seal before, in an append-only table; every read of the log or the alerts checks the chain and names any record changed or removed after sealing. Why: an audit log anyone with the database can quietly edit proves little. Limits: an entry changed before its first seal isn't caught, and a role that can rewrite the seals could hide a change; on AWS each seal is also copied to an S3 bucket with Object Lock (governance mode, a day's retention, so a prototype teardown still works; production would use compliance mode), and the check compares the newest seal with its copy.
61. **A guardian checks the agent's actions in code** (2026-11-13). Before an approval under the limit is paid, rules check it against the agent's own checklist, the screening, the amount claimed and how many model calls it took; one that fails waits for a senior handler with the reason. Why: Gartner's guardian agents enforce at the point of action, apart from the agent; rules in code can't be talked round by a claim's text, unlike a second model.
62. **Second audit: the limits the first one missed, in code** (2026-11-13). A payout is never worked out to more than the amount claimed; a file added after the hidden-instruction check is checked before a specialist reads it; a sign-off carries the amount the handler saw and is refused if it changed; the api checks a red-team report against its own payments and attack list before it can keep a candidate (one result an attack, none left out; a report naming another unpaid claim still passes, in `TODO.md`); customer memory keeps section numbers and check counts, never text the model wrote; the Copilot starts at most three claims a turn and checks a note against the whole conversation; the agents' and Copilot's roles call Claude only through Australian profiles and regions; the pipeline fails rather than passes when a plan, repository or bucket can't be read, and the teardown deletes nothing when it can't read the bootstrap. Why: an audit of the whole repo and of #117 found each one; what's left is in `TODO.md`, with the calls that are the owner's. Instead of: trusting the model's lines, the caller's report and a green run.
63. **Compare picks the claim agent's model; a person and the exam still decide** (2026-11-14). Up to three models and efforts run the same practice claims; the page answers with the cheapest that meets the targets, and the judge picks the better of two explanations blind, in both orders. Propose hands a pick to an improvement round, so nothing on the page changes the live agent. Cost guard: Opus and Fable only on 5 claims or 1, each run within the round spending limit, a comparison within three. Why: the improver tried only the models it thought of, and a 0 to 3 grade can't tell two good explanations apart. Instead of: letting an engineer switch the model directly.
64. **The red team sits under Secure, each attack aimed at a layer** (2026-11-14). Evaluate asks whether the agent is right; the red team asks whether it can be made to do wrong, which is Secure's question, and Posture and Guardrails already report its results. Each attack names the layer it's built to get past, and attacks with no instruction to spot test the layers behind the instruction check. Why: every attack stopped at the first layer, so the rest went untested. Instead of: adopting Promptfoo or garak, which test a model or an endpoint one prompt at a time rather than a claim through the portal.
65. **Pages fit the developer's window** (2026-11-14). Dashboard and console pages fit 1710×1270 without scrolling: the last row fills what's left and its list scrolls inside, and detail sections sit behind pill tabs (`design-system.md` 40). Why: the developer works on that screen, and pages either ran far past it or left a third empty. Instead of: fitting a 1440×900 laptop too, which would have meant cutting content.
