# Status

## Built

1. Scaffold (plan-claim-flow phase 1): a uv workspace with `apps/api` and `apps/agent` (health endpoints only), a web app (React, Vite and TypeScript, a placeholder page; now `apps/portal` and `apps/dashboard`), a Dockerfile per app, `docker-compose.yml` with PostgreSQL 17, and the `apps` workflow running each app's checks.
2. Context layer (phase 2): `apps/context`, an MCP server at `/mcp` (port 8006) with seven read-only lookups over data governance's seven files, each answer naming its source; DNS-rebinding protection limits it to the laptop and Compose host names.
3. The `api` (phase 3): claims, policies, customers, handlers, decisions, payments and steps in PostgreSQL through SQLAlchemy Core and Alembic; seeding from `data/` and the context layer (never `data/evals/`); the payout rules and claims manual section 14 checks; payments that refuse anything over the approval limit before reading the claim and pay each claim once; the local sign-in stand-in issuing Cognito-shaped ID tokens; the agent's key and handlers' tokens checked on every route. The agent's routes are scoped to one claim (`/api/agent/claims/{id}/...`), including reading its claim and steps. Handlers ask the agent to work a claim (`POST /api/staff/claims/{id}/work`), and sign-off and send-back ask it to resume, over the contract in [plan-claim-flow.md](plan-claim-flow.md); the `api` names who made each decision. The `api` tests also run on PostgreSQL 17 (`TEST_DATABASE_URL`, and the `api-on-postgres` CI job).
4. The claim agent (phase 4): `apps/agent`, a FastAPI service the `api` calls at `/work` and `/resume`. Claude Haiku 5.5 checks each claim for hidden instructions first (a flagged claim is referred and Claude Sonnet 5.5 never sees it); then a LangGraph graph runs Claude Sonnet 5.5 with strict tools (the claim, policy, history, payout and decision through the `api`, and the context layer's seven lookups over MCP), records every step and model call, has code pay an approval under the limit, and pauses a held payout until a handler signs it off or sends it back. Progress is saved in PostgreSQL after every step. `models.py` is the only module that reaches Claude, with the workspace header.
5. The handlers' dashboard (phase 5): sign-in, the queue, and the claim page with live steps, sources, the decision and its calculation, sign-off and send-back. Every response is checked with zod; each web app's `src/fixtures/` holds real api responses (`UPDATE_WEB_FIXTURES=1 uv run pytest apps/api/tests/test_web_contract.py`) that its tests parse. Served by nginx with a strict Content-Security-Policy.
6. The customers' portal ([plan-customer-portal.md](plan-customer-portal.md)), now a separate app (decision 10): `apps/portal` for customers and `apps/dashboard` for staff, each its own Vite app, image and nginx that forwards only its own api prefix (`/api/customer/` or `/api/staff/`). The api's staff and customer routes verify tokens from separate issuers, with separate signing keys and audiences (`undercover-staff`, `undercover-customer`), so one audience's token fails the other's signature check; the Cognito group is checked too. A customer sees only their own policies and claims (plain status and reason; never steps, calculations, sources or handler notes), makes a claim on their own active policy, and adds up to five receipts (JPEG, PNG or PDF by their first bytes, 5 MB each) while it waits. Receipts are kept under random names on the `receipts` Docker volume (`storage.py`); handlers see thumbnails and download them as attachments with `nosniff`; the hidden-instruction check and the claim agent read them as Claude image and document blocks marked as customer-supplied data. Both apps have the UnderCover logo and a travel illustration (copied, not shared: a shared package later); the dashboard has a header that wraps instead of clipping, and a queue whose IDs, money and dates never wrap.
7. The case brief and quick claims (spec 30–33, 43): handlers see a stage tracker (received, checked, assessed, decided, paid), a banner only when a claim needs them, and a recommendation card with the outcome, reason and the agent's checklist (exceptions first, each line with a source chip that previews it) and the payout bar; the agent's activity is in a separate rail in plain words, and the **Show trace** switch (or T) shows every step's raw JSON and each model call's tokens, cost and time (`GET /api/staff/claims/{id}/trace`). Senior handlers can override a decision with a reason code and note (`POST /api/staff/claims/{id}/override`; an approval pays at once as their sign-off; nothing paid can change). The queue opens on **Needs me** (held payouts, referrals and review requests) with J/K to move; Ctrl/⌘K opens a command palette; S, B and U on a claim go to sign-off, send-back and the queue. Customers claim photo first: receipts, a tap on what happened and a few words, then the drafting assistant (Claude Haiku through the agent's `/draft`, `POST /api/customer/drafts`, ten an hour per customer) drafts the summary, items, amounts and dates with their sources and asks only what's missing; the customer checks and sends it, and their own words stay the record. Customers follow a status tracker and can ask a person to review a decision (`POST /api/customer/claims/{id}/review-request`). Both sign-in pages are plain email and password (Google shown as coming soon on the portal) with a discreet **Use test account** button that calls a dev-only `test-sign-in` route, so no password is in the browser.
8. The Copilot (spec 53): `apps/copilot`, a LangGraph agent on Claude Sonnet 5.5 behind `/api/copilot/` (only the dashboard's nginx forwards it). It holds no api key: every request carries the handler's own staff token, which it checks with `/api/staff/me` and passes to the api through LangGraph's run context, never into a checkpoint. Its tools read the queue, a claim, a claim's steps, customers by name (`GET /api/staff/customers`) and the scoreboard when there is one, and ask the agent to work a claim; a sign-off stops on `interrupt()` with a card (claim, customer, amount, the agent's reason) and pays only when the handler presses **Sign off and pay**. Conversations are kept per handler in PostgreSQL (`copilot` schema). In the dashboard, **Copilot** in the header opens the sidebar.
9. Specialist sub-agents (spec 51): the claim agent calls `check_documents` (Claude Haiku: receipts against the story, items, amounts and the trip's dates), `find_duplicate_receipts` (code: each receipt's SHA-256 and, for images, a 64-bit difference hash kept at upload, migration `0007c`; `GET /api/agent/claims/{id}/duplicates` gives only other claim ids) and `review_medical` (Claude Haiku, for medical claims). It cites them in its checklist as "Document checker", "Duplicate check" and "Medical reviewer", and their chips preview what each found.

## Running it

10. Set up a machine once: `bash scripts/setup.sh`, then `uv sync`, and `npm ci` in `apps/portal` and `apps/dashboard`.
11. Secrets: copy `.env.example` to `.env` and fill it in. Python 3.14 (decision 9).
12. Run everything: `docker compose up --build`, then open the portal at http://127.0.0.1:5173 (customers) or the dashboard at http://127.0.0.1:5174 (staff).
13. Run without Docker: with `DATABASE_URL` set, `uv run -m undercover_api.migrate`, `uv run -m undercover_api.seed` and `uv run uvicorn undercover_api.main:create_app --factory --reload`, `uv run -m undercover_context` and `npm run dev` in `apps/portal` (port 5173) and `apps/dashboard` (port 5174).
14. Check: `uv run ruff format --check && uv run ruff check && uv run pyright && uv run pytest`, and in `apps/portal` and `apps/dashboard` `npm run lint && npm run typecheck && npm test`.
